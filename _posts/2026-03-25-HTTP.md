# HTTP 协议 完整系统学习大纲

> 本文面向**测试工程师 / 接口测试初学者**，按「认知 → 报文 → 方法/状态码/头部 → 状态与连接 → 缓存与安全 → API 设计 → 接口测试实战」组织，由浅入深。
> HTTP 不难在"背下有多少个状态码"，难在**能看懂一条裸报文、能说清一次请求到底经过了什么、能在接口报错时三秒内判断是谁的锅**。本文把这三件事讲透，命令和配置都给可直接照抄的值。
>
> TCP/IP、DNS、三次握手这些底层基础不在本文展开，见本站 [计算机网络]({%post_url 2026-04-02-计算机网络%}) 篇。

## 一、HTTP 是什么

### 1.1 一句话定义

HTTP（HyperText Transfer Protocol，超文本传输协议）是**客户端与服务器之间"要东西 / 给东西"的一套约定**：客户端按格式写一张"请求单"，服务器按格式回一张"回执单"，双方都认这个格式，通信就成立。

> 💡 **通俗类比**：HTTP 就是**点外卖的订单格式**。你得写清楚「要什么（URL）、怎么要（方法）、有什么特殊要求（头部）、备注（请求体）」；商家回你「做没做（状态码）、做了什么（响应体）、什么时候做的（Date）」。格式双方都认，订单才不会被看错。它只管**单据怎么写**，不管外卖小哥怎么走（那是 TCP/IP 的事）。

### 1.2 在网络分层里的位置

| 层 | 协议举例 | 这一层关心什么 | HTTP 在哪 |
| :--- | :--- | :--- | :--- |
| 应用层 | **HTTP**、HTTPS、DNS、FTP、MQTT、SMTP | 数据**长什么样、什么意思** | ✅ **HTTP 在这一层** |
| 传输层 | TCP、UDP | 数据怎么可靠送达、端口是多少 | HTTP/1.1、2 基于 TCP；HTTP/3 基于 QUIC(UDP) |
| 网络层 | IP、ICMP | 怎么找到对方机器 | 与 HTTP 无直接关系 |
| 链路层 / 物理层 | 以太网、Wi-Fi | 网线/信号上怎么传 | 与 HTTP 无直接关系 |

> 一句话：**HTTP 只负责"说人话"，TCP 负责"把话完整送到"，IP 负责"送到哪台机器"。** 抓包时看到的一层层封装就是这个顺序。

### 1.3 版本演进

| 版本 | 年份 | 关键变化 | 今天还用吗 |
| :--- | :--- | :--- | :--- |
| HTTP/0.9 | 1991 | 只有 `GET`，只能回 HTML，无头部 | ❌ 仅历史 |
| HTTP/1.0 | 1996 | 增加方法、状态码、头部、可传图片等 | ⚠️ 极少 |
| HTTP/1.1 | 1997 | **持久连接(Keep-Alive)**、管道化、分块传输、Host 头、缓存控制 | ✅ 仍大量使用 |
| HTTP/2 | 2015 | **二进制分帧、多路复用、头部压缩(HPACK)、服务器推送** | ✅ 主流 |
| HTTP/3 | 2022 | 基于 **QUIC(UDP)**，彻底解决队头阻塞、0-RTT 握手 | ✅ 逐步普及 |

> 版本号只是"怎么传得更快"的演进，**报文语义（方法、状态码、头部）基本没变**，所以学 1.1 的知识在 2/3 上照样适用。

### 1.4 五个核心特性

| 特性 | 意思 | 对测试的影响 |
| :--- | :--- | :--- |
| **无状态** | 服务器不记得上一次请求是谁发的 | 登录态必须靠 Cookie / Token 自己带，见第六章 |
| **客户端-服务器** | 永远是客户端主动发起，服务器被动回应 | 服务器**不能主动推**消息（要 WebSocket/SSE，见第十五章） |
| **可扩展** | 靠头部字段加功能，双方约定即可 | 常见自定义头 `X-Request-Id`、`X-Sign`，接口文档必须写清 |
| **支持缓存** | 响应可以被中间节点存下来复用 | 容易出现"我改了怎么没生效"，见第八章 |
| **支持中间节点** | 代理、网关、CDN 可以插在中间 | 502/504 常常是**网关**报的，不是业务服务，见 4.4 |

### 1.5 测试工程师为什么要吃透 HTTP

| 工作场景 | 用到了 HTTP 的什么 |
| :--- | :--- |
| 写接口用例 | 方法、URL、参数位置、Content-Type、请求头 |
| 判断 bug 归属 | 4xx / 5xx、响应头、`X-Request-Id`、网关报错 |
| 抓包定位问题 | 看裸报文、看有没有真的发出去、参数有没有被改 |
| 造异常场景 | 改状态码、改头部、模拟超时、重复提交、并发 |
| 性能/安全测试 | 连接复用、缓存命中、TLS、认证、越权 |

> 一句话：**接口测试的"接口"，本质就是一条 HTTP 报文。** 看不懂报文，就只能在工具界面上点，遇到问题只能猜。

## 二、一次完整的 HTTP 通信

### 2.1 从输入 URL 到看到页面，中间发生了什么

```text
① 浏览器解析 URL          → 拆出协议/域名/端口/路径/参数
② DNS 解析域名            → example.com → 93.184.216.34
③ 建立 TCP 连接           → 三次握手（HTTPS 还要再做 TLS 握手）
④ 客户端发送 HTTP 请求    → 请求行 + 请求头 + 空行 + 请求体
⑤ 服务器处理并返回响应    → 状态行 + 响应头 + 空行 + 响应体
⑥ 浏览器渲染 / 解析数据   → HTML 渲染页面，JSON 交给 JS 处理
⑦ 连接复用或关闭          → Keep-Alive 复用，或 Connection: close 断开
```

> 接口测试平时只关心 **④⑤**，但一旦出现超时、证书错误、502，就得往 **②③** 上查。

### 2.2 URL 结构拆解

```text
https://www.example.com:8080/api/v1/users?id=1024&status=active#profile
└─┬─┘  └──────┬───────┘ └┬┘ └────┬────┘ └────────┬────────┘ └──┬──┘
 协议        域名(主机)   端口     路径            查询参数      片段
```

| 部分 | 示例 | 说明 | 测试注意 |
| :--- | :--- | :--- | :--- |
| 协议 scheme | `https` | http / https | 写错协议会直接连不上或证书报错 |
| 域名 host | `www.example.com` | 也可直接写 IP | 域名解析失败 = 请求根本没发出去 |
| 端口 port | `:8080` | http 默认 **80**，https 默认 **443** | 测试环境常带非默认端口，漏写就打到 80 |
| 路径 path | `/api/v1/users` | 定位资源 | 大小写敏感、末尾 `/` 有时是两个接口 |
| 查询参数 query | `?id=1024&status=active` | `?` 开头，`&` 分隔 | 中文/特殊字符**必须 URL 编码**，否则 400 |
| 片段 fragment | `#profile` | 只在浏览器本地用 | **不会发给服务器**，接口里写它没意义 |

> 💡 **常见坑**：参数值里带 `&`、`=`、`空格`、中文却不编码，服务器会把一个参数拆成两个 → 表现为"参数莫名其妙丢了"。Postman 会在 Params 里自动编码，手写 URL 时最容易踩。

### 2.3 请求报文逐行拆解

```http
POST /api/v1/login HTTP/1.1
Host: www.example.com
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64)
Accept: application/json
Content-Type: application/json; charset=utf-8
Content-Length: 43
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...
Cookie: sessionId=abc123

{"username":"tester","password":"123456"}
```

| 行 | 名称 | 作用 |
| :--- | :--- | :--- |
| 第 1 行 | **请求行** | `方法 + 路径 + 协议版本`，三者用空格隔开 |
| 第 2~8 行 | **请求头** | 一行一个 `键: 值`，描述客户端身份、期望、附加信息 |
| 空行 | **CRLF 分隔** | **必须有**，用来告诉服务器"头到此为止" |
| 最后 | **请求体** | 真正要提交的数据，GET 通常没有 |

> `Host` 是 HTTP/1.1 **唯一强制必须有**的请求头（因为一台服务器可能挂多个站点），漏了会直接 400。

### 2.4 响应报文逐行拆解

```http
HTTP/1.1 200 OK
Date: Tue, 19 Nov 2026 08:30:00 GMT
Content-Type: application/json; charset=utf-8
Content-Length: 78
Set-Cookie: sessionId=abc123; Path=/; HttpOnly; SameSite=Lax
Cache-Control: no-store
X-Request-Id: req-9f2c1a

{"code":0,"message":"success","data":{"token":"eyJhbGciOi..."}}
```

| 行 | 名称 | 作用 |
| :--- | :--- | :--- |
| 第 1 行 | **状态行** | `协议版本 + 状态码 + 原因短语` |
| 第 2~7 行 | **响应头** | 内容类型、长度、Cookie、缓存策略、链路 ID |
| 空行 | 分隔 | 同样必须有 |
| 最后 | **响应体** | 业务数据，接口断言主要看这里 |

> `X-Request-Id` 这类**链路 ID**在提 bug 时非常有用：把这一串贴给开发，他能直接去日志里定位这次请求，比描述"刚才那次失败了"高效得多。

### 2.5 报文四部分与两个易错点

| 组成 | 请求报文 | 响应报文 |
| :--- | :--- | :--- |
| 起始行 | 请求行 `POST /xxx HTTP/1.1` | 状态行 `HTTP/1.1 200 OK` |
| 头部 | 请求头 | 响应头 |
| 空行 | `\r\n` | `\r\n` |
| 消息体 | 请求体（可选） | 响应体（可选） |

- **头部字段名大小写不敏感**：`content-type` 与 `Content-Type` 等价；但**值**通常区分大小写。
- **`Content-Length` 与实际体长不符**会导致截断或一直等；用工具时不用手填，手写裸报文（如 telnet）时最容易错。

### 2.6 用 curl 亲眼看到原始报文

```bash
curl -v https://httpbin.org/get?name=tester
```

`-v` 输出里，`>` 开头是**发出的请求**，`<` 开头是**收到的响应**，两边都是原始报文，没有工具美化的中间层：

```text
> GET /get?name=tester HTTP/2
> Host: httpbin.org
> User-Agent: curl/8.4.0
> Accept: */*
>
< HTTP/2 200
< content-type: application/json
< content-length: 246
<
{"args": {"name": "tester"}, ...}
```

> 接口调不通时，第一件事就是加 `-v` 看**请求到底发出去没有、URL 和头部是不是你以为的样子**——很多"接口有 bug"其实是工具把参数放错了位置。

## 三、请求方法与幂等性

### 3.1 常用方法全表

| 方法 | 语义 | 请求体 | 安全 | 幂等 | 典型用途 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `GET` | 获取资源 | ❌ 通常无 | ✅ | ✅ | 查询列表/详情 |
| `HEAD` | 只要响应头，不要体 | ❌ | ✅ | ✅ | 探活、检查资源是否存在/大小 |
| `OPTIONS` | 问服务器支持哪些方法 | ❌ | ✅ | ✅ | **CORS 预检请求**，见 11.2 |
| `POST` | 提交数据 / 触发动作 | ✅ | ❌ | ❌ | 登录、新增、下单、复杂查询 |
| `PUT` | 整体替换资源 | ✅ | ❌ | ✅ | 全量更新用户信息 |
| `PATCH` | 局部修改资源 | ✅ | ❌ | ❌ | 只改一个字段 |
| `DELETE` | 删除资源 | ❌ 可选 | ❌ | ✅ | 删除订单 |
| `TRACE` | 回显收到的请求 | ❌ | ✅ | ✅ | 诊断（生产一般禁用） |

**安全(safe)** = 只读，不改变服务器数据；**幂等(idempotent)** = 同样的请求**执行 1 次和 N 次，服务器最终状态一样**。

### 3.2 GET vs POST（破除几个流行误解）

| 对比项 | GET | POST |
| :--- | :--- | :--- |
| 参数位置 | URL 查询字符串 | 请求体（也可带 query） |
| 数据可见性 | 在 URL 里，会进浏览器历史/日志 | 在体里，不进 URL |
| 长度限制 | **受浏览器/服务器 URL 长度限制**（约 2KB~8KB） | 理论上无限制，服务端可配置上限 |
| 可缓存 | ✅ 默认可缓存 | ❌ 默认不缓存 |
| 可收藏/回退 | ✅ | ❌ 回退会提示"重新提交表单" |
| 安全性 | 都不安全（HTTP 明文），**POST 不等于加密** | 同左，安全要靠 HTTPS |

> 💡 **最大的误解**：「POST 比 GET 安全」。POST 只是把参数从地址栏挪到报文体里，**用抓包工具一样看得清清楚楚**。真正的安全只有 HTTPS 能做到。
>
> 另一个误解：「GET 不能带请求体」。协议没禁止，只是很多服务端/工具不处理，实践中不要用。

### 3.3 幂等性为什么测试必须关心

> 💡 **通俗类比**：**幂等**像电梯的"关门"按钮——按 1 次和按 10 次，门都是关着，不会出乱子；**不幂等**像"下单"按钮——按 10 次可能真的产生 10 笔订单。

| 场景 | 如果不幂等会怎样 | 测试要做什么 |
| :--- | :--- | :--- |
| 网络超时后客户端自动重试 | 重复扣款 / 重复下单 | 验证幂等键、重放同一请求结果一致 |
| 用户连点提交按钮 | 生成多条重复数据 | 前端置灰 + 后端幂等校验 |
| 消息队列重复投递 | 状态被覆盖两次 | 用唯一单号做去重 |

> 一句话：**幂等是"可以放心重试"的保证**。凡涉及写操作，测试用例里一定要加一条「同一请求连发两次，验证数据只变一次」。

### 3.4 POST / PUT / PATCH 怎么选

| 场景 | 用哪个 | 例子 |
| :--- | :--- | :--- |
| 新建，ID 由服务端生成 | `POST` | `POST /users` |
| 新建或全量覆盖，ID 客户端指定 | `PUT` | `PUT /users/1024`（整份用户信息都要传） |
| 只改其中一两个字段 | `PATCH` | `PATCH /users/1024` 只传 `{"nickname":"新名字"}` |
| 触发一个动作（登录、支付、审批） | `POST` | `POST /login` |

> 用 `PUT` 却只传一个字段，其他字段可能被**清空**——这是接口测试里很典型的"数据莫名其妙没了"的来源。

### 3.5 RESTful 中的方法映射

| 资源操作 | 方法 + 路径 | 成功状态码 |
| :--- | :--- | :--- |
| 查列表 | `GET /users` | 200 |
| 查详情 | `GET /users/1024` | 200 / 404 |
| 新建 | `POST /users` | **201** + `Location` 头 |
| 全量更新 | `PUT /users/1024` | 200 / 204 |
| 局部更新 | `PATCH /users/1024` | 200 |
| 删除 | `DELETE /users/1024` | **204**（无响应体） |

> 详细设计约定见第十六章；`OPTIONS` 与预检请求放在 11.2 单独讲。

## 四、状态码

### 4.1 五类一眼记

| 区间 | 类别 | 谁的问题 | 记忆口诀 |
| :--- | :--- | :--- | :--- |
| `1xx` | 信息响应 | 进行中 | "收到了，继续" |
| `2xx` | 成功 | 成了 | "办好了" |
| `3xx` | 重定向 | 要换个地方 / 用缓存 | "去别处 / 没变过" |
| `4xx` | **客户端错误** | **请求方** | "你写错了" |
| `5xx` | **服务器错误** | **服务方** | "我出问题了" |

### 4.2 常用状态码速查（接口测试必背）

| 码 | 名称 | 含义 | 测试关注点 |
| :--- | :--- | :--- | :--- |
| `200` | OK | 请求成功 | **不代表业务成功**，还要看响应体里的业务码 |
| `201` | Created | 创建成功 | 检查响应头 `Location` 是否指向新资源 |
| `204` | No Content | 成功但**无响应体** | 别写"解析 JSON"的断言，会失败 |
| `206` | Partial Content | 分片/断点续传 | 配合 `Range` 请求头，见 12.4 |
| `301` | Moved Permanently | 永久重定向 | **会被浏览器强缓存**，改回来很麻烦 |
| `302` | Found | 临时重定向 | 常见于登录跳转；注意 POST 可能被改成 GET |
| `304` | Not Modified | **走缓存，没传响应体** | 缓存命中标志，见第八章 |
| `307` | Temporary Redirect | 临时重定向，**保持原方法和体** | 比 302 更严格 |
| `308` | Permanent Redirect | 永久重定向，保持方法 | 301 的严格版 |
| `400` | Bad Request | 参数/格式不对 | 先查 JSON 格式、必填项、编码 |
| `401` | Unauthorized | **未认证**（没带/带错凭证） | 查 Token、Cookie 有没有带上、有没有过期 |
| `403` | Forbidden | **已认证但没权限** | 越权测试的重点：换个低权限账号应返回 403 |
| `404` | Not Found | 资源/路径不存在 | 查 URL 拼写、环境、版本号 |
| `405` | Method Not Allowed | 方法用错了 | 用 GET 调了只支持 POST 的接口 |
| `408` | Request Timeout | 请求超时 | 客户端发太慢 |
| `409` | Conflict | 资源冲突 | 重复创建、版本冲突 |
| `415` | Unsupported Media Type | `Content-Type` 不支持 | 典型：传 JSON 却写成表单类型 |
| `422` | Unprocessable Entity | 格式对但语义校验失败 | 参数类型对、值不合法（很多框架用它替代 400） |
| `429` | Too Many Requests | **被限流** | 压测/脚本跑太快常见，看 `Retry-After` |
| `500` | Internal Server Error | 服务端代码异常 | 提 bug 附 `X-Request-Id` 让开发查日志 |
| `502` | Bad Gateway | **网关**收到了上游的无效响应 | 多半是后端服务挂了/没起来 |
| `503` | Service Unavailable | 服务不可用（过载/维护） | 重启、扩容、限流中 |
| `504` | Gateway Timeout | **网关等上游超时** | 后端处理太慢，不是网络断 |

### 4.3 3xx 重定向：301/302/307/308

| 码 | 永久性 | 是否允许把 POST 改成 GET | 典型用途 |
| :--- | :--- | :--- | :--- |
| 301 | 永久 | ⚠️ 允许（历史行为） | 域名换址、HTTP 跳 HTTPS |
| 302 | 临时 | ⚠️ 允许（历史行为） | 登录后跳回原页面 |
| 307 | 临时 | ❌ 严格保持方法和体 | API 临时迁移 |
| 308 | 永久 | ❌ 严格保持方法和体 | API 永久迁移 |

> 💡 **测试坑**：301 会被浏览器**长期缓存**，就算服务端改回原地址，浏览器也不再请求原 URL。所以测试环境别用 301，验证重定向逻辑时也要注意 Postman 默认会自动跟随（可关掉 `Automatically follow redirects` 才能看到真实的 302）。

### 4.4 4xx / 5xx：三秒判断"谁的锅"

| 现象 | 大概率原因 | 先查什么 |
| :--- | :--- | :--- |
| 4xx | 请求写错了 | 方法、URL、参数、头部、认证态 |
| 5xx | 服务端炸了 | 把 `X-Request-Id` + 时间贴给开发查日志 |
| 502 / 504 | **网关或上游**的问题，不一定是本服务 | Nginx / 网关配置、后端实例是否存活 |
| 200 但业务失败 | 业务码非 0 | 看响应体 `code` / `message`，不是 HTTP 的错 |
| 一直转圈 | 超时 / 连接池满 | 看耗时、服务端线程、网关超时配置 |

> 一句话：**4xx 先照镜子改自己的请求，5xx 先记下链路 ID 找开发。** 别把 400 提给后端，也别把 500 自己默默改参数绕过。

### 4.5 最容易混淆的四组

| 组 | 区别 |
| :--- | :--- |
| `401` vs `403` | 401 = "**你是谁？**"（没登录）；403 = "**我知道你是谁，但你不能干这个**"（没权限） |
| `400` vs `422` | 400 = 报文格式/参数就不对；422 = 格式对但业务校验不通过（框架差异大，看接口文档） |
| `404` vs `405` | 404 = 这个地址不存在；405 = 地址在，但方法用错了 |
| `502` vs `504` | 502 = 上游给了个**看不懂/无效**的响应；504 = 上游**根本没回**，等到超时 |

### 4.6 业务码 ≠ HTTP 状态码（重点）

很多接口无论成功失败都返回 `200`，真实结果放在响应体里：

```json
{
  "code": 1003,
  "message": "余额不足",
  "data": null,
  "requestId": "req-9f2c1a"
}
```

```text
HTTP/1.1 200 OK          ← 只能说明"这次通信成功了"
body.code = 1003         ← 业务失败了，这才是断言重点
```

> **断言必须两层都写**：先断言 HTTP 状态码（通信层），再断言业务码 + 关键字段（业务层）。只断 200 的用例会漏掉所有业务失败。JMeter / Postman / pytest 里都一样，见第十七章。

## 五、HTTP 头部

### 5.1 头部按作用分五类

| 类别 | 出现位置 | 举例 |
| :--- | :--- | :--- |
| 通用头 | 请求/响应都有 | `Cache-Control`、`Connection`、`Date` |
| 请求头 | 只请求 | `Host`、`Accept`、`Authorization`、`Cookie`、`User-Agent`、`Referer` |
| 响应头 | 只响应 | `Server`、`Set-Cookie`、`Location`、`ETag` |
| 实体头（内容头） | 描述消息体 | `Content-Type`、`Content-Length`、`Content-Encoding`、`Content-Disposition` |
| 自定义头 | 双方约定 | `X-Request-Id`、`X-Sign`、`X-Timestamp` |

### 5.2 常用请求头逐字段

| 头 | 作用 | 测试注意 |
| :--- | :--- | :--- |
| `Host` | 目标主机（1.1 强制） | 工具自动带，手写报文别漏 |
| `User-Agent` | 客户端身份 | 有些接口按 UA 做兼容/风控，脚本里最好模拟真实值 |
| `Accept` | 期望**响应**格式 | `application/json`；与 `Content-Type` 别搞混 |
| `Content-Type` | **请求体**的格式 | 传 JSON 却是 `x-www-form-urlencoded` → 415 或参数为空 |
| `Authorization` | 认证凭证 | `Bearer xxx` / `Basic xxx`，见第十章 |
| `Cookie` | 带回服务器种的 Cookie | 见第六章 |
| `Referer` | 从哪个页面跳来的 | 防盗链、CSRF 校验会看它 |
| `Accept-Encoding` | 可接受压缩 | `gzip, deflate, br`，服务端据此压缩响应 |
| `X-Forwarded-For` | 经过代理时的原始 IP | 网关/负载均衡场景常用 |

> 💡 **最高频的坑**：`Accept`（我**想要**什么格式）和 `Content-Type`（我**发过去**的是什么格式）方向相反，写反了就是 415 或取不到参数。

### 5.3 常用响应头逐字段

| 头 | 作用 |
| :--- | :--- |
| `Content-Type` | 响应体格式 + 字符集，决定解析器怎么读 |
| `Content-Length` | 响应体字节数 |
| `Set-Cookie` | 服务端下发 Cookie（可多条） |
| `Location` | 重定向目标（配合 3xx）或新建资源地址（配合 201） |
| `Cache-Control` / `ETag` / `Last-Modified` | 缓存控制，见第八章 |
| `Access-Control-Allow-*` | 跨域许可，见第十一章 |
| `Content-Encoding` | 响应实际用的压缩算法 |
| `Content-Disposition` | 附件下载时的文件名，见 12.4 |
| `Server` | 服务器软件（生产常特意隐藏） |
| `X-Request-Id` | 链路追踪 ID，提 bug 必贴 |

### 5.4 Content-Type 常见值

| 值 | 用于 | 典型形态 |
| :--- | :--- | :--- |
| `application/json` | **最主流**的接口数据 | `{"name":"tester"}` |
| `application/x-www-form-urlencoded` | 传统表单提交 | `name=tester&age=20` |
| `multipart/form-data` | **文件上传**（带 boundary） | 见 12.3 |
| `text/plain` | 纯文本 | 有些签名接口要求原文 |
| `text/html` | 网页 | 接口返回它通常说明**打到了错误页** |
| `application/xml` | 老系统 / SOAP | `<user>...</user>` |
| `application/octet-stream` | 二进制下载 | 文件流 |

> 接口返回 `text/html` 却期望 JSON，十有八九是**被网关/登录页拦截了**（例如未登录被 302 到登录页，工具自动跟随了重定向）。先看响应体前几个字符是不是 `<!DOCTYPE html>`。

### 5.5 内容协商：Accept 三兄弟

| 请求头 | 协商什么 | 示例 | 响应对应头 |
| :--- | :--- | :--- | :--- |
| `Accept` | 数据格式 | `application/json, text/plain` | `Content-Type` |
| `Accept-Encoding` | 压缩算法 | `gzip, br` | `Content-Encoding` |
| `Accept-Language` | 语言 | `zh-CN,zh;q=0.9` | `Content-Language` |

`q=0.9` 是权重（0~1，越大越优先），没有 `q` 默认 1.0。

> 测试多语言接口时，改 `Accept-Language` 就能验证文案是否按语言返回，不用换账号或改配置。

### 5.6 自定义头与三个测试坑

- **大小写不敏感**：`x-request-id` 与 `X-Request-Id` 一样，但断言时按文档写，别自己改大小写。
- **签名类头常带时间戳**：`X-Sign` + `X-Timestamp` 组合有有效期，脚本录一遍再回放会失效，需要动态生成。
- **重复头**：同名头出现多次时各框架取值策略不同（取第一个 / 最后一个 / 逗号拼接），造异常用例时可以专门测。

## 六、Cookie、Session 与 Token（状态管理）

### 6.1 "无状态"到底是什么意思

> 💡 **通俗类比**：你每天去同一家咖啡店，但**店员每次都不认识你**。想证明"我是会员、我上一单还没取"，只能自己掏出一张卡给他看。HTTP 就是那个没记性的店员，**Cookie / Token 就是那张卡**。

| 无状态带来的好处 | 带来的麻烦 |
| :--- | :--- |
| 服务器不用存每个客户端的上下文，容易横向扩容 | 每次请求都得自带身份凭证 |
| 请求可以被任意节点处理，天然适合负载均衡 | 登录态、购物车这些"跨请求状态"要另想办法 |
| 报文简单、可缓存 | 凭证丢了/过期了，用户就"掉线" |

### 6.2 Cookie 的工作机制

```text
① 第一次请求（未登录）     客户端 → 服务器：POST /login  （带账号密码）
② 服务器种 Cookie          服务器 → 客户端：Set-Cookie: sessionId=abc123; HttpOnly
③ 浏览器自动保存           把这条 Cookie 和域名绑定存起来
④ 之后的每次请求           客户端 → 服务器：Cookie: sessionId=abc123  （浏览器自动带上）
⑤ 服务器认得你了           查到对应会话，返回登录后才有的数据
```

> 关键点：**`Set-Cookie` 由服务器下发，`Cookie` 由客户端自动回带**，中间不需要写代码。但在接口测试工具里得自己管（见 6.5）。

### 6.3 Cookie 属性全表

```http
Set-Cookie: sessionId=abc123; Domain=.example.com; Path=/; Max-Age=3600; HttpOnly; Secure; SameSite=Lax
```

| 属性 | 作用 | 测试 / 安全意义 |
| :--- | :--- | :--- |
| `Domain` | 允许发送给哪些域名 | 设为 `.example.com` 则子域共享 |
| `Path` | 允许发送给哪些路径 | `Path=/api` 则 `/web` 下不带 |
| `Expires` | 绝对过期时间（日期） | 老写法 |
| `Max-Age` | 相对有效期（秒），**优先级高于 Expires** | 0 = 立即删除；不写 = 会话级，关浏览器就没 |
| `HttpOnly` | **禁止 JS 读取** | 缓释 XSS 窃取 Cookie，安全测试必查项 |
| `Secure` | **只在 HTTPS 下发送** | HTTP 环境带不上，表现为"本地能登录，线上掉线" |
| `SameSite` | 限制跨站携带，防 CSRF | `Strict` 最严 / `Lax` 默认 / `None` 必须配 `Secure` |

> 💡 **测试高频坑**：接口在测试环境（HTTP）能通，换到预发（HTTPS）就 401 —— 十有八九是 Cookie 带了 `Secure` 而请求走的是 http，或者 `SameSite=None` 没配 `Secure` 被浏览器丢弃。

### 6.4 三种状态保持方案对比

| 方案 | 状态存在哪 | 服务器要存吗 | 优点 | 缺点 |
| :--- | :--- | :--- | :--- | :--- |
| **Cookie + Session** | 凭证在 Cookie，数据在服务器内存/Redis | ✅ 要 | 可随时强制踢人下线、好管控 | 多节点要共享 Session（常配 Redis） |
| **Token（JWT）** | 全在客户端那串 Token 里 | ❌ 不用 | 天然适合分布式、移动端友好 | **签发后难以主动作废**，泄露风险高 |
| **URL 重写 / 隐藏表单** | 拼在 URL 或表单隐藏域 | ✅ | 兼容禁用 Cookie 的老浏览器 | 易泄露、难维护，现已少用 |

> 一句话：**Session 是"存柜台、给你张取货票"，Token 是"把货直接写在你随身带的纸条上"**。前者好管控，后者好扩展。

### 6.5 接口测试里怎么带认证态

```bash
# 方式一：curl 手动带 Cookie
curl -H "Cookie: sessionId=abc123" https://api.example.com/user/profile

# 方式二：curl 用 -c/-b 自动保存与回带 Cookie
curl -c cookies.txt -X POST -d "user=tester&pwd=123" https://api.example.com/login
curl -b cookies.txt https://api.example.com/user/profile

# 方式三：Bearer Token
curl -H "Authorization: Bearer eyJhbGciOiJIUzI1NiJ9..." https://api.example.com/user/profile
```

```python
# requests：Session 对象会自动管理 Cookie
import requests
s = requests.Session()
s.post("https://api.example.com/login", json={"user": "tester", "pwd": "123"})
r = s.get("https://api.example.com/user/profile")   # 无需手动带 Cookie
```

| 工具 | 怎么做 |
| :--- | :--- |
| Postman | 登录请求后 Cookie 自动进 Cookie Manager；或用 `Authorization` 页签选 Bearer，把登录接口返回的 token 存成环境变量，后续请求直接引用该变量 |
| JMeter | **HTTP Cookie 管理器**自动处理；Token 用「JSON 提取器 + 后置处理器」提取并设为变量，见 [Jmeter]({%post_url 2026-03-17-Jmeter%}) 篇 |
| Python requests | `requests.Session()` 自动管理，见 [requests]({%post_url 2026-10-22-requests%}) 篇 |

> 💡 Postman 里推荐在登录请求的 Tests 页签把 token 写入环境变量，后续接口在 `Authorization` 页签选 Bearer 并引用该变量，避免每个请求手动复制一串长 Token。

### 6.6 会话安全三个必查点

1. **凭证是否可预测 / 是否超时**：退出登录、改密码后旧 Token/Cookie 应立即失效。
2. **敏感 Cookie 是否带 `HttpOnly` + `Secure`**：浏览器控制台执行 `document.cookie` 不应读到会话 ID。
3. **越权**：换一个低权限用户的凭证去调管理员接口，应返回 403（不能只靠前端隐藏按钮）。

## 七、连接管理

### 7.1 从短连接到长连接

| 阶段 | 做法 | 问题 |
| :--- | :--- | :--- |
| HTTP/1.0 默认 | **每个请求新建一次 TCP 连接**，回完就断 | 一个网页几十个资源 = 几十次三次握手，慢 |
| HTTP/1.0 改良 | `Connection: keep-alive` 显式声明 | 需要双方都支持 |
| HTTP/1.1 默认 | **持久连接默认开启**，同一连接可复用多个请求 | 要显式写 `Connection: close` 才断开 |

> 💡 **通俗类比**：短连接像每说一句话就重新拨一次电话；长连接像拨通后把想说的都说完再挂。省掉反复拨号的时间。

### 7.2 管道化与队头阻塞

**管道化(pipelining)**：不等上一个响应回来，就连续发多个请求。但服务器**必须按请求顺序回**，于是：

> 💡 **通俗类比**：超市只开一个收银台，前面那位顾客的商品扫不出来，后面所有人哪怕只买了一瓶水也得干等 —— 这就是**队头阻塞(HoL Blocking)**。

因为队头阻塞 + 各家实现兼容差，管道化实际很少用，浏览器基本没开。真正解决它的是 HTTP/2。

### 7.3 HTTP/2 四大改进

| 特性 | 解决什么 | 通俗说法 |
| :--- | :--- | :--- |
| **二进制分帧** | 文本报文解析慢、易出错 | 从"写信"改成"标准化集装箱" |
| **多路复用** | ✅ **解决队头阻塞** | 一个连接上开多条独立车道，某条堵了不影响别的 |
| **头部压缩(HPACK)** | 每次都重复发一大堆相同头部 | 只发"和上次不一样的部分" |
| **服务器推送** | 客户端要一个个来要 | 服务器提前把 CSS/JS 一起送来（实际使用已减少） |

> 注意：HTTP/2 **不改变**方法、状态码、头部的语义，只是换了传输方式。接口测试用例一条都不用改。

### 7.4 HTTP/3 与 QUIC

HTTP/3 把传输层从 TCP 换成基于 UDP 的 **QUIC**：

| 改进 | 说明 |
| :--- | :--- |
| 彻底解决队头阻塞 | TCP 层的丢包重传仍会卡住所有流；QUIC 每条流独立，丢包只影响自己 |
| 握手更快 | 合并 TLS 与传输握手，支持 0-RTT 复连 |
| 连接迁移 | 手机从 Wi-Fi 切到 4G，IP 变了连接不断 |

### 7.5 连接相关的测试现象

| 现象 | 可能原因 |
| :--- | :--- |
| 压测跑一会儿大量超时 | 连接池耗尽、服务端 `keep-alive` 超时太短、端口耗尽 |
| 响应头有 `Connection: close` | 服务端主动不复用，压测时握手开销会明显变大 |
| 抓包看到很多 `TCP Retransmission` | 网络丢包/拥塞，不是接口逻辑问题 |

> 压测时**优先复用连接**（JMeter 勾 Keep-Alive、requests 用 Session），否则测的是握手性能而不是接口性能，详见 [Jmeter]({%post_url 2026-03-17-Jmeter%}) 篇。

## 八、缓存机制

### 8.1 为什么需要缓存

> 💡 **通俗类比**：每天都要用的东西，与其每次跑一趟仓库，不如放一个**家门口的储物柜**，柜上贴张纸条写「这瓶水 3 天内有效」。过期了再去仓库问一句「换新的没？」——没换就继续用柜里那瓶。前者是**强缓存**，后者是**协商缓存**。

| 缓存类型 | 存在哪 | 谁用 |
| :--- | :--- | :--- |
| 私有缓存 | 浏览器本地 | 只给当前用户 |
| 共享缓存 | CDN、代理服务器、网关 | 给很多用户共用 |

### 8.2 强缓存：不问服务器，直接用

| 响应头 | 说明 | 优先级 |
| :--- | :--- | :--- |
| `Cache-Control: max-age=3600` | 相对时间，3600 秒内直接用本地副本 | **高**（有它就不看 Expires） |
| `Cache-Control: no-cache` | ⚠️ **名字骗人**：不是"不缓存"，是"每次都要去协商" | — |
| `Cache-Control: no-store` | **真正不缓存**（登录、敏感数据常用） | — |
| `Cache-Control: public/private` | 允许共享缓存 / 只允许浏览器私有 | — |
| `Cache-Control: immutable` | 内容永不变化，连协商都省了 | 常配版本化文件名 |
| `Expires: <绝对日期>` | HTTP/1.0 老写法，依赖客户端时钟 | 低 |

> `no-cache` 与 `no-store` 是**面试高频陷阱**：前者会缓存但每次校验，后者压根不存。

### 8.3 协商缓存：问一句"变了没"

| 第一对（时间） | 第二对（内容指纹） |
| :--- | :--- |
| 响应 `Last-Modified: Wed, 08 Jan 2026 ...` | 响应 `ETag: "v3-a1b2c3"` |
| 后续请求 `If-Modified-Since: <那个时间>` | 后续请求 `If-None-Match: "v3-a1b2c3"` |
| 没变 → **304 Not Modified**（无响应体） | 没变 → **304 Not Modified**（无响应体） |

`ETag` 优先级更高、更精确（能识别"内容改了但时间戳没变"或 1 秒内多次修改）。

### 8.4 完整缓存决策流程

```text
发起请求
  ↓
本地有缓存吗？ ── 没有 ──→ 正常请求服务器（200 + 完整响应体）
  ↓ 有
还在 max-age 有效期内？ ── 是 ──→ 【强缓存】直接用本地副本，不发请求
  ↓ 否
带上 If-None-Match / If-Modified-Since 去问服务器
  ↓
服务器判断变没变 ── 没变 ──→ 【协商缓存】304，无响应体，用旧副本
                 ── 变了 ──→ 200 + 新内容 + 新缓存头
```

### 8.5 一组典型响应头

```http
HTTP/1.1 200 OK
Content-Type: text/css; charset=utf-8
Cache-Control: public, max-age=31536000, immutable
ETag: "a3f5c9"
Last-Modified: Tue, 10 Nov 2026 02:00:00 GMT
```

```http
HTTP/1.1 304 Not Modified
Cache-Control: public, max-age=31536000
ETag: "a3f5c9"
```

> 304 **没有响应体**，所以断言"响应体内容"的脚本遇到 304 会失败——这是接口自动化里偶发的诡异问题，关掉缓存或校验 304 分支即可。

### 8.6 测试怎么验证缓存 / 常见"改了没生效"

| 场景 | 现象 | 处理 |
| :--- | :--- | :--- |
| 前端发了新版，用户还是旧页面 | 强缓存没过期 | 文件名带 hash（`app.a3f5c9.js`）或改 URL 版本号 `?v=2` |
| 接口返回 304，脚本断言失败 | 协商缓存命中 | 请求头加 `Cache-Control: no-cache` 强制回源 |
| 抓包看不到请求 | 强缓存直接命中，**请求根本没发出去** | 浏览器勾选 Disable cache / 强制刷新 `Ctrl+F5` |
| 登录态接口被缓存 | 共享缓存把 A 用户数据给了 B | 敏感响应必须 `Cache-Control: no-store, private` |

> 浏览器 DevTools 里 Size 列显示 `(disk cache)` / `(memory cache)` 就是命中缓存；**强制刷新**会带 `Cache-Control: no-cache` 回源，这是排查"改了没生效"最快的验证手段。

## 九、HTTPS 与 TLS

### 9.1 HTTP 明文的三个风险

| 风险 | 后果 | 通俗说法 |
| :--- | :--- | :--- |
| **窃听** | 账号密码、Token 被中间节点看到 | 寄明信片，路上谁都能看 |
| **篡改** | 响应内容被插入广告/改数据 | 明信片被人改了几个字 |
| **冒充** | 连到假网站 | 有人冒充收件人 |

HTTPS = **HTTP + TLS(SSL)**，本身不是新协议，只是在 HTTP 和 TCP 之间加了一层加密。

### 9.2 对称加密 vs 非对称加密

> 💡 **通俗类比**：**对称加密**像同一把钥匙既能锁又能开——快，但钥匙怎么安全交给对方是个难题；**非对称加密**像"公开的挂锁 + 私藏的钥匙"——任何人都能用挂锁把盒子锁上，但只有持私钥的人能打开，慢但解决了钥匙传递问题。

| | 对称加密（AES 等） | 非对称加密（RSA / ECDHE） |
| :--- | :--- | :--- |
| 密钥 | 双方同一把 | 公钥公开、私钥保密 |
| 速度 | 快 | 慢（差几个数量级） |
| TLS 里的角色 | **真正加密数据** | **只在握手阶段用来安全协商出对称密钥** |

> 所以 TLS 是「用非对称加密**商量**出一把临时对称密钥，之后全程用对称加密传数据」——兼顾安全和速度。

### 9.3 数字证书与 CA

证书解决的是"我怎么确认这把公钥真是 example.com 的，而不是中间人伪造的"：

> 💡 **通俗类比**：证书像**带公章的身份证**，CA（证书颁发机构）就是派出所。浏览器内置了信任的派出所名单，验到公章不认识/过期/域名对不上，就弹「您的连接不是私密连接」。

证书里包含：域名、公钥、有效期、颁发者、CA 的数字签名。校验失败常见原因：证书过期、域名不匹配、自签名证书、系统时间不对。

### 9.4 TLS 握手简化流程

```text
① Client Hello       客户端：我支持哪些加密套件 / TLS 版本 + 随机数A
② Server Hello       服务端：选定套件 + 随机数B + 把【证书】发过来
③ 验证证书           客户端：验 CA 签名、域名、有效期 ✅
④ 密钥协商           客户端用证书公钥加密"预主密钥"发给服务端（服务端用私钥解）
⑤ 生成会话密钥       双方用 随机数A + 随机数B + 预主密钥 算出同一把对称密钥
⑥ 切换加密           双方发 Finished，之后所有 HTTP 报文都加密传输
```

### 9.5 HTTP vs HTTPS 对比

| 项 | HTTP | HTTPS |
| :--- | :--- | :--- |
| 默认端口 | 80 | **443** |
| 传输 | 明文 | TLS 加密 |
| 证书 | 不需要 | 需要 CA 证书（可免费申请） |
| 报文结构 | 完全一样 | 完全一样（只是被加密装进 TLS 记录） |
| 性能 | 略快 | 握手有额外开销，可用会话复用/HTTP2/3 摊薄 |
| 抓包 | 直接看到明文 | 需装代理证书并让客户端信任，见 [抓包工具]({%post_url 2026-10-21-抓包工具%}) 篇 |

> **HTTPS 不等于"绝对安全"**：它只保护传输链路，防不了 XSS、CSRF、越权、SQL 注入这些应用层问题（见第十三章）。

### 9.6 测试相关：三类常见现象

| 现象 | 原因 |
| :--- | :--- |
| `SSL certificate problem: self signed certificate` | 测试环境用自签名证书，脚本需临时跳过校验（**仅限测试环境**）或用 `-k`（curl）/ `verify=False`（requests） |
| 页面部分资源加载不了（混合内容） | HTTPS 页面里引用了 `http://` 的图片/脚本，被浏览器拦截 |
| 手机抓 HTTPS 包全是乱码/看不到 | 未安装并信任代理证书，或 App 做了证书绑定(SSL Pinning) |

> 小程序、App 基本强制 HTTPS，抓包第一步永远是**装证书 + 信任**，详见 [抓包工具]({%post_url 2026-10-21-抓包工具%}) 篇。

## 十、认证与授权

### 10.1 认证 vs 授权

> 💡 **通俗类比**：**认证(Authentication)** 是"查身份证，确认你是谁"；**授权(Authorization)** 是"查门禁权限表，确认你能进哪几间房"。401 是没带身份证，403 是带了但没权限。

### 10.2 Basic 与 Digest

```http
Authorization: Basic dGVzdGVyOjEyMzQ1Ng==
```

`Basic` 后面是 `用户名:密码` 做 **Base64 编码**：

```bash
echo -n "tester:123456" | base64        # → dGVzdGVyOjEyMzQ1Ng==
echo -n "dGVzdGVyOjEyMzQ1Ng==" | base64 -d   # → tester:123456
```

> ⚠️ **Base64 是编码不是加密**，一秒就能解回明文。所以 Basic **必须配 HTTPS**，生产里基本只用于内部简单接口。Digest 用哈希挑战避免了明文传输，但复杂度高、现在也少用。

### 10.3 Bearer Token 与 JWT

```http
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.eyJ1c2VyIjoidGVzdGVyIn0.xxxx
```

JWT 是三段用 `.` 拼起来的字符串：

```text
Header（算法）. Payload（用户信息/过期时间）. Signature（防篡改签名）
 eyJhbGci...   .      eyJ1c2Vy...        .    SflKxwRJ...
   ↑ 前两段只是 Base64 编码，任何人都能解出来看，别往里放密码
```

| 注意点 | 说明 |
| :--- | :--- |
| 前两段可解码 | **不是加密**，敏感信息不能放 Payload |
| 无状态 | 服务端不存，签发后**难以主动作废**（只能靠短过期时间 + 黑名单） |
| 过期字段 | `exp`，脚本里 Token 过期是 401 最常见原因 |

### 10.4 API Key 与签名

| 方式 | 做法 | 常见于 |
| :--- | :--- | :--- |
| API Key | 头部或参数带一个固定 key：`X-Api-Key: abc` | 开放平台、内部服务 |
| HMAC 签名 | 把「参数 + 时间戳 + 密钥」按约定排序后算哈希，放 `X-Sign` | 支付、金融、对外网关 |

> 签名类接口的**时间戳有有效期**（常见 5 分钟），所以录制好的脚本隔天回放会失败，必须每次动态生成签名和 timestamp。这类接口也常要求**参数按字典序排序**，写脚本时最容易漏。

### 10.5 OAuth 2.0 四种模式

| 模式 | 适用 | 特点 |
| :--- | :--- | :--- |
| **授权码模式** | 有服务端的 Web 应用 | ✅ 最安全最常用，用 code 换 token，token 不暴露给浏览器 |
| 简化/隐式模式 | 纯前端 SPA | token 直接回给浏览器，已不推荐 |
| 密码模式 | 自家第一方 App | 用户把密码交给客户端，仅限高度信任场景 |
| 客户端凭证模式 | **服务对服务**（无用户参与） | 用 `client_id + client_secret` 换 token，接口自动化常见 |

授权码模式简化流程：

```text
用户点"微信登录" → 跳到授权页 → 用户同意 → 带 code 回调
→ 服务端用 code + client_secret 换 access_token
→ 之后请求带 Authorization: Bearer <access_token>
```

### 10.6 认证失败排查表

| 现象 | 先查 |
| :--- | :--- |
| 401 | 头有没有带？`Bearer` 后面有没有多空格？Token 过期没？ |
| Token 明明对却 401 | 是不是拿错了环境的 Token（测试/预发不通用） |
| 403 | 账号权限不够 / 越权被拦 / IP 白名单 |
| 签名校验失败 | 时间戳是否过期、参数排序、密钥、编码（UTF-8）是否一致 |
| Postman 能通、脚本不通 | 对比两边**实际发出的头部**，用 `-v` 或抓包逐项比对 |

## 十一、CORS 跨域

### 11.1 同源策略

**同源 = 协议 + 域名 + 端口三者完全相同**。只要有一个不同就是跨域：

| 当前页面 | 请求目标 | 是否同源 |
| :--- | :--- | :--- |
| `https://a.com/index` | `https://a.com/api/user` | ✅ 同源（路径不同没关系） |
| `https://a.com` | `http://a.com/api` | ❌ 协议不同 |
| `https://a.com` | `https://api.a.com` | ❌ 域名不同（子域也算） |
| `https://a.com` | `https://a.com:8080` | ❌ 端口不同 |

> 同源策略是**浏览器的限制**，不是服务器限制。所以 **Postman / curl / JMeter 从来不受 CORS 影响** —— 这点在定位问题时极其关键。

### 11.2 简单请求 vs 预检请求

满足以下**全部**条件才是简单请求，否则先发 `OPTIONS` 预检：

| 判定条件 | 简单请求允许的 |
| :--- | :--- |
| 方法 | 仅 `GET` / `HEAD` / `POST` |
| 自定义头 | 只能有少数安全头（`Accept`、`Content-Type` 等） |
| `Content-Type` | 仅 `text/plain`、`application/x-www-form-urlencoded`、`multipart/form-data` |

> **`application/json` 不在简单请求白名单里** —— 所以现在前后端分离项目里，一个带 JSON 体的 POST **几乎必然触发预检**。这是最常踩的一条。

预检请求实样：

```http
OPTIONS /api/v1/users HTTP/1.1
Host: api.example.com
Origin: https://web.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type, authorization

HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://web.example.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE, OPTIONS
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Max-Age: 86400
```

> 预检通过（204）后，浏览器才发**真正的 POST**。抓包时看到"一个接口发了两次"，第二次才是业务请求，别误判成重复提交。

### 11.3 常见 CORS 响应头

| 响应头 | 作用 |
| :--- | :--- |
| `Access-Control-Allow-Origin` | 允许的来源（具体域名或 `*`，**带凭证时不能是 `*`**） |
| `Access-Control-Allow-Methods` | 允许的方法 |
| `Access-Control-Allow-Headers` | 允许的请求头 |
| `Access-Control-Allow-Credentials: true` | 允许携带 Cookie（同时前端要 `withCredentials`） |
| `Access-Control-Max-Age` | 预检结果缓存秒数，减少 OPTIONS 次数 |
| `Access-Control-Expose-Headers` | 允许前端 JS 读到哪些响应头（默认读不到自定义头） |

### 11.4 浏览器控制台报错怎么读

| 报错关键词 | 原因 |
| :--- | :--- |
| `No 'Access-Control-Allow-Origin' header` | 服务端完全没返回 CORS 头 |
| `Method ... is not allowed by Access-Control-Allow-Methods` | 预检里的方法没被允许 |
| `Request header field x-token is not allowed` | 自定义头没写进 `Allow-Headers` |
| `The value of the 'Access-Control-Allow-Origin' header must not be '*'` | 带了 Cookie/凭证却用了通配符 |

### 11.5 测试视角：最经典的"工具通、浏览器不通"

> 💡 **一句话判定**：**Postman / curl 正常，浏览器控制台报 CORS** → 100% 是服务端 CORS 配置问题，**不是接口 bug**，也别让前端用代理"绕过去"当修复（生产不一定有代理）。修的是响应头，不是代码逻辑。

## 十二、数据格式、编码与文件传输

### 12.1 三种提交格式对比

| 格式 | `Content-Type` | 典型形态 | 什么时候用 |
| :--- | :--- | :--- | :--- |
| JSON | `application/json` | `{"name":"tester","age":20}` | ✅ 现代接口首选，支持嵌套/数组 |
| 表单 | `application/x-www-form-urlencoded` | `name=tester&age=20` | 传统表单、部分老接口、OAuth token 请求 |
| 混合表单 | `multipart/form-data` | 多段 + boundary | ✅ **文件上传**，可同时带文本字段 |

### 12.2 选错格式的典型表现

| 错误 | 结果 |
| :--- | :--- |
| 传 JSON 却写 `x-www-form-urlencoded` | 服务端取不到字段（全为空）或 415 |
| 传表单却写 `application/json` | JSON 解析失败 → 400 |
| 上传文件却用 `application/json` | 二进制被当文本处理，文件损坏 |
| 传了中文却没声明 `charset=utf-8` | 乱码 |

> Postman 里选 `raw + JSON` 会自动设 `Content-Type`；但选了 `raw` 后**没把右侧下拉从 Text 改成 JSON**，就会发出 `Content-Type: text/plain` —— 这是"参数明明填了，后端说没收到"的头号原因。Python requests 里 `data=` 与 `json=` 的区别见 [requests]({%post_url 2026-10-22-requests%}) 篇。

### 12.3 multipart/form-data 报文实样

```http
POST /api/upload HTTP/1.1
Host: api.example.com
Content-Type: multipart/form-data; boundary=----FormBoundary7MA4
Content-Length: 342

------FormBoundary7MA4
Content-Disposition: form-data; name="desc"

测试图片
------FormBoundary7MA4
Content-Disposition: form-data; name="file"; filename="test.png"
Content-Type: image/png

<这里是文件的二进制内容>
------FormBoundary7MA4--
```

- `boundary` 是分隔符，**每段以 `--boundary` 开头，整体以 `--boundary--` 结束**。
- 每个 part 有自己的 `Content-Disposition` 和可选 `Content-Type`。
- **boundary 由工具自动生成**，手写时不要自己乱填，也不要在正文里出现同样的字符串。

### 12.4 文件上传与下载

| 场景 | 关键头 / 状态码 | 测试点 |
| :--- | :--- | :--- |
| 上传 | `multipart/form-data`、`Content-Type`(part 级) | 大小上限、类型白名单、空文件、超长文件名、同名覆盖 |
| 下载 | `Content-Disposition: attachment; filename="report.pdf"` | 文件名中文乱码、文件内容校验(MD5)、权限 |
| 断点续传 | 请求 `Range: bytes=1000-` → 响应 **206** + `Content-Range` | 续传后文件拼接是否完整 |
| 大文件 | `Transfer-Encoding: chunked`（分块，事先不知道总长） | 内存占用、超时、流式读取 |

> 用 `Content-Length` 还是 `chunked`：服务端能提前算出大小就用前者；边生成边发（如导出大报表）就只能分块，此时**没有 `Content-Length`**，脚本别写死长度断言。

### 12.5 压缩与传输编码

```http
# 请求
Accept-Encoding: gzip, deflate, br

# 响应
Content-Encoding: gzip
Vary: Accept-Encoding
```

| 概念 | 说明 |
| :--- | :--- |
| `Accept-Encoding` | 客户端声明"我能解哪几种压缩" |
| `Content-Encoding` | 服务端告知"这份响应用了哪种压缩" |
| `Transfer-Encoding: chunked` | 传输方式（分块），**不是压缩** |
| `Vary` | 告诉缓存"按 Accept-Encoding 区分副本"，配错会把 gzip 内容发给不支持的客户端 |

> 抓包看到响应体像乱码时，先看 `Content-Encoding` —— 工具一般会自动解压，手写脚本没解压就会把压缩字节当 JSON 解析而报错。

### 12.6 字符编码与乱码定位

```http
Content-Type: application/json; charset=utf-8
```

| 乱码现象 | 常见原因 |
| :--- | :--- |
| 中文变 `???` 或 `æµ‹è¯•` | 请求/响应没声明或未真正用 UTF-8 |
| URL 参数里的中文丢/错 | 没做 URL 编码（百分号编码） |
| 下载文件名乱码 | `Content-Disposition` 的 filename 编码浏览器兼容问题 |

> 排查顺序：**确认报文里的编码声明 → 确认文件/字符串真实编码 → 确认显示端（终端/编辑器）编码**，三者一致才不乱码。

## 十三、安全实践

### 13.1 常见 Web 攻击

| 攻击 | 干什么 | 通俗类比 | 主要防御 |
| :--- | :--- | :--- | :--- |
| **XSS** | 把恶意脚本注入页面执行 | 在留言板里塞了张会自动转账的纸条 | 输出转义、CSP、`HttpOnly` Cookie |
| **CSRF** | 冒用已登录用户身份发请求 | 你没点，但有人替你按了"转账" | CSRF Token、`SameSite`、校验 `Referer`/`Origin` |
| 点击劫持 | 用透明 iframe 骗你点 | 按钮上面盖了层看不见的玻璃 | `X-Frame-Options` / CSP `frame-ancestors` |
| 中间人 | 窃听/篡改传输 | 明信片被人换了几行 | **HTTPS** + HSTS |
| 越权 | 改 ID 就能看别人数据 | 拿自己房卡开了别人房门 | 服务端每次都校验归属 |

> 对测试来说，**越权**是最容易手工验证、也最容易暴雷的一项：把请求里的 `userId` 改成别人的，看能不能返回数据。

### 13.2 安全响应头全表

| 头 | 作用 |
| :--- | :--- |
| `Strict-Transport-Security` (HSTS) | 强制浏览器只用 HTTPS 访问，防降级 |
| `Content-Security-Policy` (CSP) | 限制脚本/资源只能从哪加载，**XSS 主力防御** |
| `X-Content-Type-Options: nosniff` | 禁止浏览器猜 MIME 类型 |
| `X-Frame-Options: DENY` / `SAMEORIGIN` | 禁止被 iframe 嵌套 |
| `Referrer-Policy` | 控制跳转时带多少 Referer 信息 |
| `Permissions-Policy` | 限制摄像头/定位等浏览器能力 |

### 13.3 一份完整的安全响应头示例

<details markdown="1">
<summary>展开：一组较完整的安全头（可直接给开发参考）</summary>

```http
HTTP/1.1 200 OK
Strict-Transport-Security: max-age=31536000; includeSubDomains
Content-Security-Policy: default-src 'self'; script-src 'self'; object-src 'none'
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
Referrer-Policy: strict-origin-when-cross-origin
Cache-Control: no-store
Set-Cookie: sessionId=abc123; HttpOnly; Secure; SameSite=Lax
```

> 注意 `Cache-Control: no-store` 也是安全项：含个人信息的页面不该被共享缓存存下来。

</details>

### 13.4 测试工程师能做的 6 项检查

1. 全站是否强制 HTTPS，HTTP 是否 301/308 跳过去。
2. 敏感 Cookie 是否带 `HttpOnly` + `Secure` + 合理 `SameSite`。
3. 安全响应头有没有配（浏览器 DevTools → Network → Headers 一眼看完）。
4. 改 ID / 换低权限账号 → 是否 403（水平、垂直越权各测一遍）。
5. 输入框塞 `<script>alert(1)</script>` → 是否被转义而不是执行。
6. 退出登录 / 改密后，旧 Token 与旧 Cookie 是否立即失效。

## 十四、性能优化

### 14.1 三个方向

| 方向 | 思路 | 手段 |
| :--- | :--- | :--- |
| **少发** | 减少请求次数 | 合并文件、雪碧图、内联小资源、缓存 |
| **发少** | 减小单次体积 | gzip/br 压缩、图片压缩、精简 JSON 字段、分页 |
| **走近** | 缩短传输距离与时间 | CDN、HTTP/2/3、连接复用、预连接 |

### 14.2 具体手段速查

| 手段 | 做法 | 对应 HTTP 知识 |
| :--- | :--- | :--- |
| 合并请求 | 多个小图标合成雪碧图、JS/CSS 合并 | 减少握手与队头阻塞 |
| 压缩 | `Accept-Encoding: gzip, br` | 12.5 |
| 缓存 | 静态资源 `max-age` + 文件名带 hash | 第八章 |
| CDN | 静态资源放边缘节点 | 共享缓存 + DNS |
| HTTP/2 / 3 | 多路复用，不用再做域名分片 | 第七章 |
| 预连接 | `<link rel="preconnect">` / `preload` | 提前握手 |
| 延迟加载 | 图片/非首屏资源滚动到再请求 | 减少首屏请求数 |

> ⚠️ **域名分片（把资源分散到多个域名）是 HTTP/1.1 时代的技巧**，到了 HTTP/2 多路复用下反而有害（多建连接、无法复用），别照搬老优化文章。

### 14.3 缓存策略最佳实践

| 资源 | 建议 |
| :--- | :--- |
| 带内容 hash 的静态文件 `app.a3f5c9.js` | `Cache-Control: public, max-age=31536000, immutable` |
| HTML 入口页 | `Cache-Control: no-cache`（每次协商，保证能拿到新版引用） |
| 接口 / 个人数据 | `Cache-Control: no-store, private` |

### 14.4 用 Network 面板看什么

| 看哪里 | 说明 |
| :--- | :--- |
| **Waterfall 瀑布图** | 哪些请求在排队（队头阻塞）、哪个最慢 |
| **TTFB** | 首字节时间，反映服务端处理 + 网络，不含下载 |
| **Size 列** | `(disk cache)` = 命中缓存；两行里上面是传输大小、下面是解压后大小 |
| **Status 列** | 304 = 协商缓存；灰色 200 常是缓存 |
| **Timing 页签** | DNS / TCP / TLS / 等待 / 下载各段耗时，超时定位靠它 |

> 性能问题先用 Timing 分段定位：**DNS/TCP/TLS 慢**是网络或连接问题，**Waiting(TTFB) 慢**基本是服务端处理慢，别一上来就怪前端。

## 十五、协议扩展与实时通信

HTTP 是"一问一答"，想要服务器主动推消息就得用扩展方案。

### 15.1 WebSocket

```http
# 先用 HTTP 做一次升级握手
GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
```

> 握手成功后就**脱离 HTTP**，变成一条全双工长连接，双方都能随时发消息。适合聊天、实时行情、协同编辑。`101` 就是"协议切换成功"的那个状态码。

### 15.2 SSE（Server-Sent Events）

```http
GET /events HTTP/1.1
Accept: text/event-stream

HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive

data: {"price": 12.5}

data: {"price": 12.8}
```

单向（服务器 → 客户端）、基于普通 HTTP、断线自动重连，适合通知、进度、日志流。

### 15.3 三种"实时"方案对比

| 方案 | 方向 | 复杂度 | 适用 |
| :--- | :--- | :--- | :--- |
| 短轮询 | 客户端定时问 | 最低 | 实时性要求低、兼容老环境 |
| 长轮询 | 服务器 hold 住直到有数据 | 中 | 兼容性强、实时性一般 |
| **SSE** | 服务器单向推 | 低 | 通知、进度、股价推送 |
| **WebSocket** | 双向 | 较高 | 聊天、游戏、协同 |

### 15.4 其余扩展（了解即可）

| 扩展 | 说明 |
| :--- | :--- |
| WebDAV | 基于 HTTP 的方法扩展（PROPFIND/MKCOL 等），把服务器当网盘操作 |
| HTTP/2 Server Push | 服务器提前推送资源；因命中率与实现问题，实际使用已明显减少 |
| **MQTT** | 不是 HTTP 扩展，是**物联网场景**的独立轻量协议（发布/订阅），见本站 [MQTT协议]({%post_url 2026-04-14-MQTT协议%}) 篇 |

## 十六、RESTful API 设计

### 16.1 六个约束

| 约束 | 含义 |
| :--- | :--- |
| 客户端-服务器 | 前后端分离、各自独立演进 |
| **无状态** | 每个请求自带全部所需信息（见第六章） |
| 可缓存 | 响应要显式声明能否缓存 |
| 统一接口 | 用标准方法 + 资源 URL，别自造动词 |
| 分层系统 | 可插入网关/代理，客户端不必知道 |
| 按需代码（可选） | 服务器可下发脚本，实际很少用 |

### 16.2 资源与 URL 设计

| 原则 | 反例 | 正例 |
| :--- | :--- | :--- |
| 用**名词复数**，不用动词 | `GET /getUserList` | `GET /users` |
| 用路径表达层级 | `?userId=1024&type=order` | `GET /users/1024/orders` |
| 动作交给 HTTP 方法 | `POST /deleteUser` | `DELETE /users/1024` |
| 筛选/分页放 query | `/users/page/2` | `GET /users?page=2&size=20` |
| 不在 URL 里放敏感数据 | `?token=xxx` | 放 `Authorization` 头 |

### 16.3 版本管理

| 方式 | 示例 | 评价 |
| :--- | :--- | :--- |
| URL 路径 | `/api/v1/users` | ✅ 最直观、最常用 |
| 请求头 | `Accept: application/vnd.api.v2+json` | 规范但不易调试 |
| 查询参数 | `/api/users?version=2` | 简单，容易被忽略/缓存问题 |

### 16.4 统一错误格式

```json
{
  "code": 1003,
  "message": "余额不足，请充值后重试",
  "requestId": "req-9f2c1a",
  "path": "/api/v1/orders",
  "timestamp": "2026-11-19T08:30:00Z"
}
```

> 好的错误响应要满足：**业务码 + 用户可读文案 + 链路 ID**。只回一句 `"error"` 会让测试和排障都很难做。返回给用户的 `message` 里不要带 SQL、堆栈、内网 IP（信息泄露）。

### 16.5 分页、过滤、排序

| 参数 | 示例 | 说明 |
| :--- | :--- | :--- |
| 分页 | `page=2&size=20` 或 `offset=20&limit=20` | 两种风格，跟接口文档保持一致 |
| 过滤 | `status=active&role=tester` | 多值可用逗号或重复参数 |
| 排序 | `sort=-createdAt,name` | `-` 表示降序 |
| 字段裁剪 | `fields=id,name,email` | 减少传输体积 |

测试用例里别忘了边界：`page=0`、`size=0`、超大 `size`、越界页、非法 `sort` 字段。

### 16.6 文档与契约

| 工具 | 用途 |
| :--- | :--- |
| OpenAPI / Swagger | 用一份 YAML 描述全部接口，能自动生成文档与调试页面 |
| Apifox / YApi / Postman | 接口管理、Mock、自动化测试 |
| 契约测试 | 以 OpenAPI 为契约，前后端并行开发、自动生成基础用例 |

> 测试视角：**有 OpenAPI 文档就能批量生成"参数必填/类型/枚举"这类基础用例**，把人力留给业务场景。

## 十七、接口测试实战

### 17.1 curl 常用命令速查

```bash
# GET 带查询参数（& 必须加引号或用 -G --data-urlencode）
curl -G "https://api.example.com/users" --data-urlencode "name=张三" -d "page=1"

# POST JSON
curl -X POST "https://api.example.com/users" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer eyJhbGci..." \
  -d '{"name":"tester","age":20}'

# POST 表单
curl -X POST "https://api.example.com/login" \
  -d "user=tester&pwd=123456"

# 上传文件（-F 自动设 multipart/form-data）
curl -F "file=@test.png" -F "desc=测试图片" "https://api.example.com/upload"

# 只看响应头 / 只看状态码 / 存到文件
curl -I "https://api.example.com/users"
curl -o /dev/null -s -w "%{http_code} %{time_total}s\n" "https://api.example.com/users"
curl -o resp.json "https://api.example.com/users"

# 跟随重定向、跳过证书校验（仅测试环境）、打印原始报文
curl -L -k -v "https://api.example.com/users"
```

| 参数 | 作用 |
| :--- | :--- |
| `-X` | 指定方法 |
| `-H` | 加请求头（可多次） |
| `-d` | 请求体（默认 POST + 表单类型） |
| `--data-urlencode` | 自动 URL 编码，中文参数用它 |
| `-F` | multipart 表单 / 上传文件 |
| `-G` | 把 `-d` 的数据放到 URL 查询串里 |
| `-I` | 只取响应头（HEAD） |
| `-v` / `-i` | 打印原始收发报文 / 连同响应头一起输出 |
| `-o` / `-w` | 输出到文件 / 自定义输出（状态码、耗时） |
| `-L` / `-k` | 跟随重定向 / 跳过证书校验（**只用于测试环境**） |

### 17.2 三类工具怎么选

| 工具 | 强项 | 本站参考 |
| :--- | :--- | :--- |
| **Postman** | 手工调试、环境变量、用例集合、可视化 | [Postman]({%post_url 2026-03-07-Postman%}) 篇 |
| **Python requests** | 写自动化脚本、参数化、断言灵活 | [requests]({%post_url 2026-10-22-requests%}) 篇 |
| **抓包工具** | 看真实报文、弱网/断点改包、定位前后端归属 | [抓包工具]({%post_url 2026-10-21-抓包工具%}) 篇 |
| **JMeter** | 压测、批量并发、参数化关联 | [Jmeter]({%post_url 2026-03-17-Jmeter%}) 篇 |

> 定位问题时的黄金组合：**先用 Postman 复现 → 再用抓包看真实报文 → 最后用脚本固化成回归用例**。

### 17.3 一条接口的完整测试点清单

| 维度 | 至少覆盖 |
| :--- | :--- |
| **请求** | URL/方法正确；必填/选填；参数位置（query/body/path）；类型、长度、边界值；枚举值；中文与特殊字符；`Content-Type` |
| **响应** | HTTP 状态码；**业务码**；关键字段存在且类型/值域正确；响应头（含 `Content-Type`、`Set-Cookie`）；响应时间 |
| **异常** | 缺参、错参、超长、空值、非法 JSON、重复提交、并发、超时 |
| **认证** | 未登录(401)、无权限(403)、Token 过期、退出后失效 |
| **安全** | 越权（改 ID/换账号）、敏感信息不回显、注入字符被转义 |
| **状态** | 新增后能查到、删除后查不到、改一个字段不影响其他字段（PUT 陷阱） |
| **兼容/性能** | 老版本参数、分页边界、并发下数据一致性 |

> 一句话：**不要只测"正确的那条路径"**。用例的价值主要在异常和边界上。

### 17.4 "明明没问题却失败"排查表

| 现象 | 最可能的原因 |
| :--- | :--- |
| 400 | JSON 格式错、必填缺失、参数没编码、类型不对 |
| 401 | Token/Cookie 没带、过期、拿错环境 |
| 403 | 权限不足、IP 白名单、签名错 |
| 404 | URL 拼错、环境/端口错、版本号漏了 `/v1` |
| 405 | 方法用错（GET 调了 POST 接口） |
| 415 | `Content-Type` 与请求体格式不匹配 |
| 429 | 脚本跑太快被限流，看 `Retry-After` |
| 500 + 返回 HTML | 服务端异常页，别当 JSON 解析，提 bug 附 `X-Request-Id` |
| 502 / 504 | 网关/上游问题，先确认后端实例存活 |
| 返回登录页 HTML | 未登录被重定向，Postman 关掉自动跟随才看得见 302 |
| 浏览器报 CORS、Postman 正常 | 服务端 CORS 响应头没配，见第十一章 |
| 参数全为空 | 传了 JSON 却用表单类型 / `data=` 与 `json=` 混用 |
| 中文乱码 | 未声明 `charset=utf-8` 或 URL 没编码 |
| 偶发 304 | 命中协商缓存，响应体为空 |
| 请求超时 | 先看 `-v` 分段耗时，再判断是网络还是服务端慢 |

### 17.5 一个可照抄的完整示例（登录 → 带 Token 查询）

```bash
# ① 登录，把响应存下来
curl -s -X POST "https://api.example.com/login" \
  -H "Content-Type: application/json" \
  -d '{"username":"tester","password":"123456"}' \
  -o login.json

# ② 从响应里取出 token（需要 jq；Windows 可直接在 Postman 里设变量）
TOKEN=$(cat login.json | jq -r '.data.token')
echo "拿到 token: ${TOKEN:0:20}..."

# ③ 带 token 查详情
curl -s "https://api.example.com/user/profile" \
  -H "Authorization: Bearer ${TOKEN}"
```

```python
# 同样的流程用 requests 写，更适合做自动化
import requests

base = "https://api.example.com"
s = requests.Session()

login = s.post(f"{base}/login", json={"username": "tester", "password": "123456"})
assert login.status_code == 200, f"登录通信失败: {login.status_code}"
body = login.json()
assert body["code"] == 0, f"登录业务失败: {body['message']}"   # 两层断言
token = body["data"]["token"]

profile = s.get(f"{base}/user/profile", headers={"Authorization": f"Bearer {token}"})
assert profile.status_code == 200
assert profile.json()["data"]["username"] == "tester"
```

> 注意这个例子里的**两层断言**：先断 HTTP 200，再断业务 `code == 0`。只写第一层，业务失败会全部漏过去（见 4.6）。

### 17.6 断言到底写什么

| 层级 | 断言内容 |
| :--- | :--- |
| 1. 通信层 | 状态码 == 预期（200/201/204/304…） |
| 2. 业务层 | `code` / `success` / `message` 符合预期 |
| 3. 数据层 | 关键字段存在、类型正确、值符合预期、列表长度/排序 |
| 4. 头部层 | `Content-Type`、`Set-Cookie`、`Location`、`Cache-Control` |
| 5. 非功能 | 响应时间低于阈值、无敏感信息泄露 |

> 断言**别过度依赖全量 JSON 逐字节比对**——时间戳、随机 ID、排序会变，容易造出"脆弱用例"。断言关键字段 + 结构即可。
